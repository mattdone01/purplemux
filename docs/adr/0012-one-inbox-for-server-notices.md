# ADR-0012: one inbox for server-originated notices

_Epic stories: 09 (store, dispatcher, list/retry); users 10 (notes), 12 (Mission Control), 13 (deploy), 14 (watches), 26 (API-error resume) — see `_output/purplemux-portfolio-coordination/stories/`._

## Status
Accepted (2026-09-26, epic `purplemux-portfolio-coordination`, story 09).

## Context
Notes, watch firings, deploy announcements and Mission Control deliveries must reach agents in tabs the originator may not drive. Mission Control's reconcile bootstrap typed multi-line prompts into seven other workspaces' orchestrators and polled one for about 44 minutes. ADR-0008 already says an unattended dispatcher needs a composer.

## Options
1. **Per-feature delivery** (each feature calls `deliverPrompt`). Repeats the Mission Control mistake four times.
2. **Queue into the watchdog's `AutomatedPromptDispatcher`.** No readiness gate; types mid-turn; same workspace only by construction.
3. **One inbox:** one entry point, a fixed per-kind template rendered on the server, delivery only to an agent at its prompt with an empty composer, bounded refusals, visible state.

## Decision
Option 3. Watchdog nudges stay on their current path (research Q6).

- **One entry point:** `enqueueNotice({ kind, targetWorkspaceId, targetTabId, dedupeKey, fields })` (`src/lib/inbox-store.ts`). A `dedupeKey` still queued for the same target tab returns the existing item; one key may be queued once per recipient (a broadcast). There is no HTTP route that enqueues.
- **No caller text in the line** (`src/lib/inbox-templates.ts`). `deliverPrompt` submits what it types as a user turn, so the line is `[purplemux <kind> <id>] <server fields> — <pull command>`, where every field matches a grammar: server-made ids (`n-`, `w-`, `d-`, `r-`, Mission Control answer ids), workspace and tab ids (never names — names are caller-set), epoch-ms times and whole-number counts, and — for a watch, which goes only to the tab that registered it — that tab's own target (`owner/repo#n`, `owner/repo@ref`, a lease name). Mission Control ids are server-made only (a UUID or `<prefix>-<32 hex>`): producer-chosen item ids are text. A field that fails its grammar is refused, never cleaned. Subjects, reasons, titles and the epic slug are pulled (`note show`, `deploy status`, `mission answers`). The architecture allowed an epic slug the sender holds; story 09 leaves it out, because any tab may acquire `epic:<words>` and the slug would be a sender-chosen phrase in another workspace's user turn (review r1).
- **Readiness** (`src/lib/composer-readiness.ts`, extracted from Mission Control): a live session; no native permission prompt; `cliState` idle or ready-for-review, or WAITING (`busy` and `StatusManager.isWaitingAtPrompt`, ADR-0018 ruling A′ — architect ruling A′-inbox, 2026-09-26); no option list on the captured pane; an empty composer. It runs inside `withAgentDispatchLock`, after the model-policy check. Mission Control uses this same gate through the inbox since story 12.
- **Dispatcher** (`src/lib/inbox-dispatcher.ts`): a 2 s tick started beside the Mission Control runtime and stopped in `shutdownWs`. Per target tab, one item at a time, oldest first. A refusal backs off 10 s → 30 s → 2 min → 5 min. Only a state refusal (`composer-not-ready:*`) wakes early: when that tab is at its prompt again (including a stop just classified WAITING) the item is tried on the next tick. Other refusals (a permission prompt, typed text, an unreadable pane) wait out their backoff, so a busy screen never burns an attempt every 2 s. After 30 refusals, or 24 h, the item is `held` with its last refusal. A paste that throws is `held transport-uncertain`; a line still in the composer after the paste is `held stranded-in-composer`; neither is retried blind.
- **Death and retention:** `tab-closed` drops the tab's `queued` and `held` items (`target-tab-closed`); the owning feature re-routes. A tab that closed while the server was down fired its event before the inbox listened, so `startInbox` runs a boot pass over the live layouts. A drop needs positive absence: the workspace list and the layout were read and do not name the tab. An unreadable store or layout is a refusal (`target-unresolved`), never a drop, because a drop is final. The dispatcher resolves its target with a layout read that never writes: `getLayout` (used by `findTab`) replaces an unreadable layout with a default one, which fires a close for every tab. `delivered`, `dropped` and `held` items are pruned 7 days after their last transition.
- **Visibility:** `GET /api/cli/inbox?workspaceId=` (read scope) / `purplemux inbox list -w WS [--all]`; `purplemux inbox retry ID` (the target workspace's token or admin) re-queues a held item once.
- **Authority stays with the features.** The inbox never decides who may notify whom: notes (any resolved caller may send; the recipient decides whether to read), watches (only the watch's own tab), deploy (admin or the `deploy:purplemux` holder), Mission Control (its existing rules).

## Why this does not weaken the drive guard (B-1)
`canDriveWorkspace` refuses caller-supplied user-turn input into another workspace. The inbox line carries none: every field is a server-made id, a server-resolved id, a time or a count. What a sender controls is that a fixed, pull-only notice appears, and when. The one caller-derived field is a watch target, and a watch notice goes only to the tab that registered the watch. Review round 1 (H4) rejected an earlier "sanitised 120-character subject" as a cross-workspace channel.

## Consequences
One place to bound, observe and test delivery; Mission Control's retry loop no longer types anything (story 12). A recipient that stays unready gets `held` and visible, never 45 blind attempts. `~/.purplemux/inbox.json` is one Node process's file under one promise mutex, written tmp + rename, mode 0600; a file that is not `{ items: [...] }` is refused, not read as empty.

## Amendment — Mission Control on the inbox (story 12, consult ruling A′)

- Mission Control answer deliveries and reconcile-bootstrap entries are `mission` notices. The answer line is `[purplemux mission <answerId>] an answer is ready at <time> — purplemux mission answers -w <WS>; ack it with the command shown there after applying it`; the bootstrap line is `[purplemux mission boot-<32 hex>] Mission Control asks this orchestrator to reconcile — read: purplemux mission bootstrap -w <WS>`, where `boot-…` is a hash the server makes, never the caller's bootstrap id. The exact ack command (`ackCommand` in `mission answers`) and the reconcile steps (`mission bootstrap`) are pulled; no item title, run text or bootstrap id is typed.
- **Where a row waits.** While its notice waits, the Mission Control row is `queued` with no `next_attempt_at` and the marker `inbox:<itemId>` (`last_error` for a delivery, `reason` for a bootstrap entry). No new state and no schema change: every existing writer (`run.resumed` with or without answer transfer, `attention.cancelled`, ack, bootstrap confirmation) already treats `queued` as "nothing typed". `dispatching` keeps its meaning — "a paste may be in flight" — and only the paste-time preflight enters it.
- **Per-kind preflight** (`registerInboxPreflight`, in memory). The dispatcher calls a kind's preflight inside `withAgentDispatchLock`, after readiness and the still-queued check, immediately before the paste. `mission` items are never typed without one (`preflight-unregistered` is a refusal inside the bound). Mission Control's preflight checks that the row still waits on this item for this tab and that the bound agent is the same live identity, then claims the row to `dispatching` and re-runs the store's validation; a refusal drops that item only (`preflight:<reason>`).
- **Outcomes.** Delivered → `submitted` (at the delivery time); held (30 refusals or 24 h, `transport-uncertain`, `stranded-in-composer`, `target-not-agent`) → `held` with the inbox reason; dropped → `held inbox-dropped:<reason>`. A queued notice whose row left the waiting state is withdrawn (`mission-record-not-waiting`). A row handed off again (after `run.resumed` moved it) always gets a NEW notice and the old one is withdrawn (`mission-rehanded`): reusing it, as the consult first ruled, lets a reused item's in-flight rejection leave the row waiting on a dropped item (story 12 review r1). Mission Control's own 5 s/15 s/60 s retry schedule is gone: the inbox owns backoff and the bound.
- **Restart.** `recoverDispatching` runs once per process before the preflight is registered; a row caught mid-paste is `held server-restarted-during-uncertain-delivery` and its notice is withdrawn, so a crash between a paste and its record never types it twice. Only a failed recovery runs recovery again.
